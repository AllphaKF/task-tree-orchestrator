# 定时任务巡检协议（管理者侧）

> 人类可通过定时任务驱动管理者定期巡检执行者并推进轮次。
> 本协议是「定时任务提示词」的生成依据与执行规范：管理者为每个定时任务生成一份提示词
> （含本协议 + 该执行者档案 + 树当前状态摘要），存盘后交给人类配置进定时任务系统。
> 本协议吸收了多轮实测经验，各条规则均有出处；不得因"本轮简单"而跳过任何一步。

## 第 0 步：铁律——绝不打断正在运行的轮次

任何新出现的人类决定、新结论、新信息，一律「先记下、下一轮再下发」，绝不在轮次运行中追加。

1. 运行中的轮次**不追加、不纠正、不插话**——不管新决定多重要、多简单。
2. 即使新结论与运行中轮次正在做的事**直接矛盾**，也留到下一轮处理；中途插入会制造难以归因的文件变更与状态漂移（实测教训：曾因此让执行者空转追查 10 分钟以上的"状态漂移"）。
3. 轮次运行期间**不触碰执行者正在或可能进行工作的文件区域**：本枝 Results/BlockedBy/NeedsAuthorization 三区、todolist「执行者提交区」、本轮提示词指定的产出文件、执行者本轮依赖的基线文件——管理者的回填/修正/删改一律排在轮次之间做。**管理者可在执行者运行期间并行其他工作**：树文件的追加类记录（rounds.md / TREE.md / B0 台账 / 记忆回写）可照常进行；管理者自己的产出用不同文件名落盘，并标注「与执行者 RXX 并行进行」。
4. 正确姿势：新决定写入树（B0-governance.md 决策记录 + todolist.md）与记忆，成为**下一轮提示词的输入**。
5. 「是否在运行」的判定方法见第 2 步。

## 第 1 步：读树（事实源，而非聊天记录）

读取 `task-tree/TREE.md`、`rounds.md`、`todolist.md`、各枝文件。**一切以树为准**；聊天记录/规划对话可能滞后，发现与实际不符时以树的实测状态为准，并把发现记入 todolist.md 待纠。

- **项目根扫描**：对照上轮记录的文件清单，扫描项目根新出现或异常变更的规范类/状态类文件（docs/、根目录 *.md、*.json 等）；发现后按权威顺序复核并记入 todolist.md。

## 第 2 步：判定执行者状态（按执行者档案的方法，必须看底层事件，不能只看界面）

本节举例来自 Codex 执行者实测；不同执行者环境的事件格式与判据以执行者档案为准。

- **首选判据**：解析执行者环境的底层事件记录（如会话 JSONL 的 task_started / task_complete 配对、后者是否带 error）。**仅看到交付消息还不够**——执行者可能重连后重新生成一次完整交付，此时轮次并未结束。
- **UI 辅证**：运行状态指示（如"运行时状态行/加载图标"）= 未结束；该指示消失才是结束信号。但**没有它不等于已结束**，必须回到底层事件确认。
- **勿信文件 mtime**（常冻结在创建时刻）：改用 size + 行数两次采样对比判断是否仍在写入。
- **重连是假象**：自动重连中属正常自愈，不可据此判为异常；必须回到轮次事件确认。

三种情况（每轮必判定其一）：

- **① 仍在运行** → 本轮巡检直接终止，不干预，等下一轮。期间任何新决定只写树与记忆，不发出去、不改文件。
- **② 已完成**（结束事件且无 error）→ 进入第 3 步及之后。
- **③ 未完成 / 传输错误**（"stream disconnected before completion"类，或执行者明确表示未做完）→ 在**现有会话内**回复「继续」或经审核的授权内容作为收尾，然后终止本轮。**不新开对话**（曾因轮次标注错误被纠正）。
  - 先看其末尾是否已完整产出：若已完整，再投「继续」会触发重连重生成循环（实测曾 18 分钟内重复同一段话 6 次），此时跳过回复，直接进入第 3 步核验。

## 第 3 步：核验交付 + 生成下一轮提示词

1. **先自己核验项目实测状态，不要只信执行者的报告**：跑测试命令、比对关键文件哈希与状态值、确认基线未动（基线清单见该枝本轮提示词的「收尾核验」节）。
2. 读执行者本轮交付，判断质量与是否真完成任务；**核验落盘以文件实际存在/大小为准**（实测教训：执行者自述"已写入"但文件从未落盘）。
3. 检查是否越权：对照该枝 Limitations 逐条核验产出与动作记录。
4. 给执行者指定「核对来源」前，**必须先自己确认来源文件真的覆盖待核字段**（实测教训：来源范围过窄会报假阳性缺陷）。
5. 按 `round-prompt-template.md` 生成下一轮提示词，必须满足：
   - 写明**完整项目绝对路径**（路径写错是常见空转原因，实测曾空转 7 分钟自查目录）；
   - **轻量设计**：任务拆小、每步立即落盘、单轮 ≤ 20 分钟；禁止长时间批量循环与复杂正则（长轮次几乎必然触发传输层中断）；
   - 带**硬边界**（转写自该枝 Limitations）；
   - 附**环境坑绕行写法**（转写自执行者档案）；
   - 明确要求执行者**全程用指定语言**（默认中文）。
6. **以目的为导向**：判断本轮工作是否服务于任务真实目的；只为流程完整而堆砌的轮次应被质疑并替换。
7. **当唯一阻塞是人类决策时**：不要空开纯等待轮——改为降低人类决策摩擦（演练操作路径、出具并排说明书），或直接向人类提问要求裁定。

## 第 4 步：投递

- 按执行者档案的通道投递（新开对话/继续现有对话按第 2 步判定结果）。
- **投递前必须确认：不要在上一个轮次仍在运行时投递**。判定见第 2 步。两个会话并行写同一批文件会产生难以归因的变更（实测教训），**无例外**——即使旧轮次已声明只读。
- **投递前权限模式检查**：确认执行者环境权限模式符合人类要求（跳过模式而非自动模式等）；不符先纠正再投递。
- **人类在场保护**：发现人类正在操作机器（前台窗口活跃、输入框有未发送内容、会话生成中等）→ 不执行任何投递类 computer-use 操作；提示词只存盘（续投稿），本轮终止并向人类说明。
- 同理，等待期间不改任何项目文件（见第 0 步）。
- 提示词先**存盘备份**（`task-tree/rounds/prompts/round-R<序号>-prompt.md`），投递细节（UI 坐标、快捷键、剪贴板编码、发送判据）以执行者档案为准，档案里每条都来自实测。
- **投递失败降级**：投递失败重试后仍失败（粘贴丢失、user_interference 等）→ 降级为人工投递（提示词全文呈给人类粘贴），记录降级原因与方式；不得反复空转重试。
- **会话上下文管理（执行者只接收命令）**：每轮投递**新建对话**（改名「落地环节-<N>」）——执行者上下文只含本轮提示词，省 token、命令清晰；旧对话完整留存供管理者复查；执行者一切事实以树与提示词为准，不得引用历史旧信息。

## 第 5 步：投递后验证 + 回写树

- **验证投递完整性**：确认提示词首句与末段完整、新轮次已启动、会话名/编号正确（判据见执行者档案；例如会话索引出现新记录、输入框清空回占位符等）。
- **回写树**：rounds.md 追加本轮记录；更新各枝状态；把执行者呈递的等待项/待授权项并入 todolist.md 与 TREE.md 决策清单。**一切记录只追加、不覆写、不删除**（谁/何时/原因；错误用新记录更正，绝不改旧记录）。
- **回写执行者档案**：本轮新踩的坑（投递、判定、环境）立即记入档案——环境知识靠档案逐轮沉淀，不靠聊天记忆。
- **基线一旦变化，必须显式记录新值**，并同步标注「哪些文档引用了旧值、需要更新」（实测教训：拿着作废哈希做比对会产生假异常）。
- **回写记忆**（管理者侧）：本轮闭合情况、交付物、基线变化、下一轮待办、待人类决策清单。

## 第 6 步：向人类呈递「待你决策」清单（每轮必做，人类可能缺席多轮）

**先分 Gate 与非 Gate 轮**：非 Gate 轮次**不打扰人类**——问题累积进 todolist.md 与决策清单，在下一轮次自行消化；**到达 Gate 节点（见 TREE.md）才向人类呈递**，且呈递格式为**质量判断报告 + 固定三选项（①通过 ②需要修复（附具体修复项）③放弃）**，让人类三选一，不呈递原始清单。

**为什么单列**：人类不一定每轮都在。历轮提出的问题很可能至今未处理；若每轮只报新增问题，待办就会在轮次间丢失，导致反复空转。

1. **先读上轮记录**找历轮未决事项，来源按可靠性排序：树（B0-governance.md 决策台账 + 各枝 NeedsAuthorization 区）→ 记忆中的决策清单 → 聊天记录（可能滞后，仅作补充）。
2. **再核对是否已解决**——不要照搬旧清单：用项目实测状态验证（回填字段是否已写入、文件哈希是否已变、勾选项状态）。已解决移除，未解决保留。
3. **累积呈递，用列表形式，不要用表格**（人类偏好）：历轮累积未决 + 本轮新增，合并成一份列表，在回复末尾呈递。
4. **每项写清五要素**：①要做什么；②在哪做（文件路径+字段/行号）；③可选值与限制；④做完走哪条分支；⑤已连续等待轮数。
5. **标注阻塞等级**：区分「阻塞主线、必须人类来」与「可延后、不挡路」。
6. 若某项已连续多轮未处理，显式写出「已连续 N 轮等待」。
7. `AskUserQuestion` 只在人类明显在线且该轮需要即时互动时使用，不要默认用它打断。

## 定时任务提示词的结构（管理者生成，交给人类配置）

```
你是「<任务名>」任务树的管理者大模型。按 task-tree-orchestrator skill 的
scheduler-protocol 执行本轮巡检。项目根：<绝对路径>。树位置：<路径>/task-tree/。
执行者档案：<路径>/task-tree/executors/<执行者名>.md（先读它）。
本轮触达后依次执行：第 0 步铁律 → 第 1 步读树 → 第 2 步判定状态（规则①②③）
→ 第 3 步核验+生成下一轮 → 第 4 步投递 → 第 5 步验证+回写 → 第 6 步呈递决策清单。
全程中文回复。
```
