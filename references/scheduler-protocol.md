# 定时任务巡检协议（管理者侧）· 多执行者版

> 人类可通过定时任务驱动管理者定期巡检执行者并推进轮次。
> 本协议是「定时任务提示词」的生成依据与执行规范：管理者为每个定时任务生成一份提示词
> （含本协议 + 该执行者档案 + 树当前状态摘要），存盘后交给人类配置进定时任务系统。
> 本协议吸收了多轮实测经验，各条规则均有出处；不得因"本轮简单"而跳过任何一步。

**【P2】通道分支（先读这一句）**：本协议含**两种模式**，巡检开始前必须先按「第 0 步 0.1」选定模式：

- **模式 A：独立巡检者版**（P2 权威表述，**默认条文**）——定时任务唤醒**独立巡检者**（非管理者本身），做**机械循环**：逐路判定 → 呈报管理者 → 从交接台取件投递 → 验证并回写交接台。核验与轮次生成归管理者。
- **模式 B：子 agent 同步通道版**（子 agent 同步通道变体）——子 agent 为**同步调用**，返回即判知完成，**巡检者环节豁免**、由管理者兼判定；**免「取件投递」环节**，交接台降级为**投递登记台**（`PENDING.md` 现状形态）。
- **共用**：第 0 步铁律、第 1 步读树、第 3 步（管理者核验 + 生成轮次）、第 5 步回写树、第 6 步呈递决策清单——两模式措辞一致，**不因模式不同而降低要求**。
- **分叉点仅两处**：第 2 步的判定判据、第 4 步的投递形态。下文凡标 **「(A)」/「(B)」** 的段落为模式专属；未标注者两模式通用。

**通用流程骨架（两模式不变）**：

```
触发 → 铁律检查（运行中则不干预，按执行者逐个判定）→ 判定（逐路，规则①②③）
     → 核验交付 / 生成下一轮提示词（管理者）→ 存盘 → 投递（A: 交接台分路取件 / B: 并列 Agent 调用）
     → 投递后验证 → 回写树与交接台/登记台 → 向人类呈递累积决策清单（含并行组汇聚）
```

## 第 0 步：模式选择 + 铁律——绝不打断正在运行的轮次

### 0.1 模式选择规则（每轮巡检的第一件事：先定模式，再干活）

| 执行者类型 / 通道形态 | 采用模式 | 依据 |
|---|---|---|
| **人工投递 / 多窗口独立对话 / UI 定时投递**（执行者有自己的人机界面与会话概念） | **模式 A** | P2；`interfaces.md` §一 通道声明 |
| **子 agent 同步通道**（管理者在**单条消息内并列多个 Agent 调用**、同步返回，无独立会话） | **模式 B** | 子 agent 同步通道；`interfaces.md` §一 |

- **判定依据**：执行者档案的「通道」字段 + `interfaces.md` §一 的通道声明。**以 interfaces.md 为准**（它是通道形态的权威声明），档案提供操作细节。
- **混合工程逐路选择**：同一棵树里部分路为人工投递、部分路为子 agent 时——**按路选模式**，同一轮巡检中 A/B 可并存，按路判定、按路处置；**不要求全工程统一一种模式**，也不得因"另一路用的是 B"而给子 agent 套用 A 的判据。
- **模式变更**（执行者通道更换）→ 属管理者动作：在 `interfaces.md` 记明变更原因与时间，本协议条文不改（这正是「双模式并置」的目的——无需回滚条文）。
- **两模式共用铁律**：不打扰运行中轮次、先完成先核验、先审后合、只追加不覆写。

### 0.2 铁律（两模式共用）——绝不打断正在运行的轮次

任何新出现的人类决定、新结论、新信息，一律「先记下、下一轮再下发」，绝不在轮次运行中追加。

1. 运行中的轮次**不追加、不纠正、不插话**——不管新决定多重要、多简单。
2. 即使新结论与运行中轮次正在做的事**直接矛盾**，也留到下一轮处理；中途插入会制造难以归因的文件变更与状态漂移（实测教训：曾因此让执行者空转追查 10 分钟以上的"状态漂移"）。
3. 轮次运行期间**不触碰该执行者正在或可能进行工作的文件区域**：本枝 Results/BlockedBy/NeedsAuthorization 三区、todolist「执行者提交区」（`todolist/<执行者名>.md`）、**该执行者的临时写区 `task-tree/staging/<执行者名>/`**、本轮提示词指定的产出文件、执行者本轮依赖的基线文件、**交接台/登记台 `PENDING.md` 中该路的待投与投递中条目**——管理者的回填/修正/删改一律排在轮次之间做。
   **【P3】管理者可在执行者运行期间并行其他工作**：树文件的追加类记录（rounds.md / TREE.md / B0 台账 / 记忆回写）、**其他路**的核验与投递、管理者自己的产出（用不同文件名落盘，并标注「与执行者 RXX 并行进行」）可照常进行。
4. **【P2】按执行者逐个适用，不是全局冻结**：多路并行时，上述「不打扰」**以执行者为单位**——路① 运行中只冻结路① 的接触面，不影响路②/路③ 的判定、核验与投递。**禁止把「有任一路在运行」扩大解释为「全工程冻结」**（试点已实测三路并行投递，全局冻结与既成事实矛盾）。
5. 正确姿势：新决定写入树（B0-governance.md 决策记录 + `todolist/manager.md`）与记忆，成为**下一轮提示词的输入**。
6. 「是否在运行」的判定方法见第 2 步；**按路判定**，逐路得出结论。

## 第 1 步：读树（事实源，而非聊天记录）

读取 `task-tree/TREE.md`、`rounds.md`、`rounds/prompts/PENDING.md`（**各路投递登记 / 交接台状态**）、`B0-governance.md`（**依赖矩阵与并行组标定**）、`todolist/`（`manager.md` / `human.md` / `sub-*.md`）、各枝文件。**一切以树为准**；聊天记录/规划对话可能滞后，发现与实际不符时以树的实测状态为准，并把发现记入 `todolist/manager.md` 待纠。

- **项目根扫描**：对照上轮记录的文件清单，扫描项目根新出现或异常变更的规范类/状态类文件（docs/、根目录 *.md、*.json 等）；发现后按权威顺序复核并记入 `todolist/manager.md`。
- **【P2】读后先答三问**（写进本轮记录）：①本任务有哪些并行组在跑（PENDING.md 各路状态）；②哪些执行者此刻可能有 RUNNING 枝（逐路列出待判定名单）；③按 0.1 规则，各路分别采用模式 A 还是模式 B。

## 第 2 步：**逐路**判定执行者状态（巡检者只判不核验）

### 2.0 分工原则（两模式共用）

**巡检者/管理者做机械判定，管理者做核验与判断。** 对**每一个有 RUNNING 枝的执行者**（含处于「待投 / 投递中」待判状态的各路），**逐一路循环执行规则 ①②③**，每路各出一个独立判定结论。

- **(A) 模式 A**：判定由**独立巡检者**执行（定时任务唤醒），判完**逐路呈报管理者**；**巡检者不做核验、不生成轮次、不写树**——核验与轮次生成是管理者的活（第 3 步）。
- **(B) 模式 B**：子 agent 为同步调用，**巡检者环节豁免**、由**管理者兼任判定**；在 Agent 调用返回时即判知完成，无需第三方巡检者做「运行中 / 已完成 / 中断」判定。P2 独立巡检者机制**保留条文设计**，待「多窗口独立对话 / 人工投递」执行者场景再启用。
- **禁止跳路**：不得只判「正在跑的那一路」；组内其他路的完成/中断同样必须判知（漏判会导致漏核验或双投）。

### 2.1 判据（甲）——(A) 模式 A：UI / 定时通道（底层事件链，逐条保留原协议原文）

本节举例来自 Codex 执行者实测；不同执行者环境的事件格式与判据以执行者档案为准。

- **首选判据**：解析执行者环境的底层事件记录（如会话 JSONL 的 task_started / task_complete 配对、后者是否带 error）。**仅看到交付消息还不够**——执行者可能重连后重新生成一次完整交付，此时轮次并未结束。
- **UI 辅证**：运行状态指示（如"运行时状态行/加载图标"）= 未结束；该指示消失才是结束信号。但**没有它不等于已结束**，必须回到底层事件确认。
- **勿信文件 mtime**（常冻结在创建时刻）：改用 size + 行数两次采样对比判断是否仍在写入。
- **重连是假象**：自动重连中属正常自愈，不可据此判为异常；必须回到轮次事件确认。
- **逐一循环**：上述判据**对每一路分别执行**，判据来源为该路执行者档案；某路缺判据 → 记为异常分支（2.4）上报，不得用别路判据顶替。

### 2.2 判据（乙）——(B) 模式 B：子 agent 同步通道

- **同步返回即判知完成**：管理者发出 Agent 调用后**同步阻塞等待**，返回即代表该路本轮已结束；无「运行中」这一中间态可供巡检，因而**无须第三方位巡检者**。
- **完成判据**：返回文本符合本轮提示词要求（**落盘产出 + ≤5 行中文总结**），且产出文件在写区**实际存在且非空**（以文件实际存在/大小为准，不凭「已写入」自述——落盘核验属第 3 步）。
- **未完成判据**：调用**报错 / 超时**视为中断（等价于规则 ③）→ 按该轮提示词「中断恢复指引」重投；进度以落盘文件为准，未落盘步骤重做。
- **多路判定**：单条消息内并列的多个 Agent 调用**各自独立返回**，逐路按返回结果判定；**先返回先进入第 3 步核验排队（P5）**，不等待未返回的路。
- **规则 ③ 的适用限定**：「未完成 / 传输错误（"stream disconnected before completion"类）」分支**仅适用模式 A**；模式 B 下传输层错误表现为调用报错，走上面的中断重投分支。

### 2.3 三种情况（逐路必判定其一）

- **① 仍在运行** → **该路**本轮巡检直接终止，不干预，等下一轮。期间任何新决定只写树与记忆，不发出去、不改该路文件。**其余路不受影响，照常判定与推进**。
- **② 已完成**（结束事件且无 error / 模式 B 下同步返回且满足完成判据）→ 该路进入第 3 步及之后。
- **③ 未完成 / 传输错误**（模式 A："stream disconnected before completion"类，或执行者明确表示未做完；模式 B：调用报错/超时）→ 在**现有会话内**回复「继续」或经审核的授权内容作为收尾，然后终止该路本轮。**不新开对话**（曾因轮次标注错误被纠正）。
  - 先看其末尾是否已完整产出：若已完整，再投「继续」会触发重连重生成循环（实测曾 18 分钟内重复同一段话 6 次），此时跳过回复，直接进入第 3 步核验。

### 2.4 异常分支（模式 A 明文）

巡检者发现**任何异常**（断联、锁超时、通知失败、判据来源缺失）→ **不自行处置**，按既定异常分支**上报管理者**；**无新事件则本轮休眠**（休眠不等于终止定时任务）。

## 第 3 步（**管理者**）：核验交付 + 生成下一轮提示词

**本步由管理者执行，巡检者不得越位**（模式 A：巡检者的职责止于第 2 步呈报与第 4 步机械投递）。

1. **先自己核验项目实测状态，不要只信执行者的报告**：跑测试命令、比对关键文件哈希与状态值、确认基线未动（基线清单见该枝本轮提示词的「收尾核验」节）。
2. 读执行者本轮交付，判断质量与是否真完成任务；**核验落盘以文件实际存在/大小为准**（实测教训：执行者自述"已写入"但文件从未落盘）。
3. 检查是否越权：对照该枝 Limitations 逐条核验产出与动作记录（含「产出是否落在自己的写区、是否越过写区写正式工程区域」）。
4. 给执行者指定「核对来源」前，**必须先自己确认来源文件真的覆盖待核字段**（实测教训：来源范围过窄会报假阳性缺陷）。
5. 按 `references/round-prompt-template.md` 生成下一轮提示词，必须满足：
   - 写明**完整项目绝对路径**（路径写错是常见空转原因，实测曾空转 7 分钟自查目录）；
   - **轻量设计**：任务拆小、每步立即落盘、单轮 ≤ 20 分钟；禁止长时间批量循环与复杂正则（长轮次几乎必然触发传输层中断）；
   - 带**硬边界**（转写自该枝 Limitations）；
   - 附**环境坑绕行写法**（转写自执行者档案）；
   - 明确要求执行者**全程用指定语言**（默认中文）。
   - **提示词存盘命名**：统一为 `task-tree/rounds/prompts/round-R<序号>-<执行者名>-prompt.md`（**取执行者名、一路一份**，与第 4 步 4.1 / 4.3 及 `references/round-prompt-template.md` 0.4 三处一致；多执行者工程一律带执行者名，避免同名覆盖）。
6. **以目的为导向**：判断本轮工作是否服务于任务真实目的；只为流程完整而堆砌的轮次应被质疑并替换。
7. **当唯一阻塞是人类决策时**：不要空开纯等待轮——改为降低人类决策摩擦（演练操作路径、出具并排说明书），或直接向人类提问要求裁定。
8. **【P5】核验节流**：并行产出按「**先完成先核验**」排队，管理者**同一时段只核验一路**（核验本身不并行）；并行度上限与核验顺序见 `interfaces.md`（接入新并行组前**先读该文件**）。
9. **【P3】核验通过 → 下达合并指令 → 秘书执行者合并**：把写区产出移入正式工程位置并留痕「RXX 合并自 <执行者名> 写区」（记入 rounds.md 与本枝 Results）。**管理者只核验、只下指令，不亲自动手。** 核验不通过 → **产出留在写区**走纠偏轮次（瑕疵分级见协议 §3.4），**正式工程零污染、不生成回滚动作**。
10. **【P4】单枝事项不单独呈递**：不阻塞整组的待裁事项累积到该并行组的**汇聚点**，与组级结论一次呈递（见第 6 步）。

## 第 4 步：投递（两模式分叉；**绝不在运行中投递，按执行者维度**）

### 4.1 共用铁律：投递前必须确认——**该执行者**的上一轮已结束

- **【限定到执行者维度】同一执行者的上一个轮次仍在运行时，绝不得续投/再投该执行者**；判定见第 2 步（逐路）。**不同执行者可并行投递**，并行组内各路**互不等待**（P2 明文）。
- **为什么限定**：原协议原文「不要在上一个轮次仍在运行时投递……无例外」是按**单执行者全局**表述；在多路并行下若按字面执行，会把「三路同时投递」误判为违例——而三路并行正是 P1 允许且试点已实测跑通的形态。**铁律的真正目的是「不让两个写入者同时写同一批文件」**，因此约束对象是**同一执行者 / 同一批文件**，不是「全局同时只允许一路」。
- **真实风险仍然存在**：同一执行者并行写同一批文件会产生难以归因的变更（实测教训）——**这条无例外**。
- **投递前权限模式检查**：确认执行者环境权限模式符合人类要求（跳过模式而非自动模式等）；不符先纠正再投递。**(A)** 适用；**(B)** 子 agent 无独立权限模式，此项**豁免**（以 Agent 调用参数为准）。
- **人类在场保护**：发现人类正在操作机器（前台窗口活跃、输入框有未发送内容、会话生成中等）→ 不执行任何投递类 computer-use 操作；提示词只存盘（续投稿），本轮终止并向人类说明。**(A)** 适用；**(B)** 同步 Agent 调用不受此限。
- **提示词先存盘备份**：`task-tree/rounds/prompts/round-R<序号>-<执行者名>-prompt.md`（**取执行者名、一路一份，防多路互相覆盖**；命名口径与第 3 步第 5 条、4.3、`references/round-prompt-template.md` 0.4 四处一致）。
- **投递失败降级**：投递失败重试后仍失败（粘贴丢失、user_interference 等）→ 降级为人工投递（提示词全文呈给人类粘贴），记录降级原因与方式；不得反复空转重试。**(A)** 适用。

### 4.2 (A) 模式 A：按交接台分路取件投递（各路独立、互不等待）

- **交接台分路**：`task-tree/rounds/prompts/PENDING.md` 按 `[路·<执行者名>]` 分节，状态三态：**待投 / 投递中 / 已投递**。
- **独立查重**：该路的同一提示词不得双投（头两次巡检不得各投一次）；投递前先读该路状态，非「待投」不得取件。
- **独立锁**：巡检者取件后把该路置「**投递中**」占位（含投递时间与执行者标识）；投递完成后置「已投递」。
- **超时自动解锁判定**：置「投递中」超过该路执行者档案的阈值仍无进展 → 按超时处理，**解锁回「待投」并上报管理者**（不自行重投）。
- **按执行者档案的通道投递**（新开对话 / 续投按第 2 步判定结果）；投递细节（UI 坐标、快捷键、剪贴板编码、发送判据）以执行者档案为准，档案里每条都来自实测。

### 4.3 (B) 模式 B：子 agent 同步通道投递（**免取件投递**）

- **免取件**：子 agent 由管理者直接调用，**不存在「巡检者从交接台取件」环节**；交接台由「待投 / 投递中 / 已投递」的**交接台**降级为**投递登记与审计台**（记录提示词存盘路径、投递时间、返回状态）。
- **并列投递**：**在单条消息内并列投递多个 Agent 调用**（调用数 = 该并行组的并行度，不超过 `interfaces.md` 声明的上限）；各路提示词各自存盘 `round-R<序号>-<执行者名>-prompt.md`（命名口径同 4.1）。
- **先登记后投递**：投递前在 `PENDING.md` 该路条目写「提示词存盘路径 + 投递中」；同步返回后由管理者回写「已投递（RXX）——核验状态 / 返回摘要」。
- **无对话概念**：子 agent 无独立会话，**「新建对话 / 改名『落地环节-N』」条不适用**；投递后以**返回文本 + 写区落盘**判定（见 2.2）。
- **不并行写同一批文件**：同一执行者实例同一时刻只承接一路；并行组内各路写区与枝文件互不相交（P1/P3 保证）。

### 4.4 会话上下文管理（通道分叉）

**执行者只接收命令**：每轮投递只让执行者看见本轮提示词，省 token、命令清晰；历史完整留存供管理者复查；执行者一切事实以树与提示词为准，不得引用历史旧信息。

- **(A) UI / 定时通道版**：每轮投递**新建对话**（改名「落地环节-<N>」）——执行者上下文只含本轮提示词；旧对话完整留存供管理者复查。
- **(B) 子 agent 同步通道版**（子 agent 同步通道现实写法）：①本轮为**独立 Agent 调用**，无历史对话上下文；②管理者在 agent 运行期间**不追加任何消息**；③执行者事实来源**只有树文件与本轮提示词**，不得引用旧信息；④你是并行组中的一路，同一时刻另有其他路在跑——**只做本轮任务、只写自己的写区**。

## 第 5 步：投递后验证 + 回写树

- **验证投递完整性**：确认提示词首句与末段完整、新轮次已启动、会话名/编号正确（判据见执行者档案；例如会话索引出现新记录、输入框清空回占位符等）。**(B)** 以「Agent 调用已发出且返回」为验证判据。
- **【P2】回写交接台 / 登记台**：`rounds/prompts/PENDING.md` 该路状态回写（A：投递中 → 已投递；B：投递中 → 已投递（RXX）——核验状态 / 返回摘要）。
- **回写树**：rounds.md 追加本轮记录；更新各枝状态（**状态唯一源 = TREE.md 状态表**；枝文件 Status 由管理者在投递 / 收尾时同步）；把执行者呈递的等待项/待授权项并入 `todolist/manager.md` 与 TREE.md 决策清单。**一切记录只追加、不覆写、不删除**（谁/何时/原因；错误用新记录更正，绝不改旧记录）。
  - **【P1】多路轮次记录形态**：一轮可含多路，格式 `RXX：G<N> = <路①执行者>/<路②执行者>/<路③执行者> 三路并列`（试点实测实例：`G1 = sub-spec / sub-templates / sub-skeleton`）。
- **回写执行者档案**：本轮新踩的坑（投递、判定、环境）立即记入档案——环境知识靠档案逐轮沉淀，不靠聊天记忆。
- **基线一旦变化，必须显式记录新值**，并同步标注「哪些文档引用了旧值、需要更新」（实测教训：拿着作废哈希做比对会产生假异常）。
- **回写记忆**（管理者侧）：本轮闭合情况、交付物、基线变化、下一轮待办、待人类决策清单。

## 第 6 步：向人类呈递「待你决策」清单（每轮必做，人类可能缺席多轮）

**先分 Gate 与非 Gate 轮**：非 Gate 轮次**不打扰人类**——问题累积进 `todolist/manager.md` 与决策清单，在下一轮次自行消化；**到达 Gate 节点（见 TREE.md）才向人类呈递**，且呈递格式为**质量判断报告 + 固定三选项（①通过 ②需要修复（附具体修复项）③放弃）**，让人类三选一，不呈递原始清单。

**【P4】并行组汇聚**：组内全部枝 `DONE` 后，管理者**统一独立核验、合并状态，以「组级结论」一次呈递**（Gate 或决策清单）；组内单枝的待裁事项**累积到汇聚点**，不单独呈递——**除非该事项阻塞整组**（阻塞整组时立即呈递，不等汇聚）。

**为什么单列**：人类不一定每轮都在。历轮提出的问题很可能至今未处理；若每轮只报新增问题，待办就会在轮次间丢失，导致反复空转。

1. **先读上轮记录**找历轮未决事项，来源按可靠性排序：树（B0-governance.md 决策台账 + 各枝 NeedsAuthorization 区）→ 记忆中的决策清单 → 聊天记录（可能滞后，仅作补充）。
2. **再核对是否已解决**——不要照搬旧清单：用项目实测状态验证（回填字段是否已写入、文件哈希是否已变、勾选项状态）。已解决移除，未解决保留。
3. **累积呈递，用列表形式，不要用表格**（人类偏好）：历轮累积未决 + 本轮新增，合并成一份列表，在回复末尾呈递。
4. **每项写清五要素**：①要做什么；②在哪做（文件路径+字段/行号）；③可选值与限制；④做完走哪条分支；⑤已连续等待轮数。
5. **标注阻塞等级**：区分「阻塞主线、必须人类来」与「可延后、不挡路」。
6. 若某项已连续多轮未处理，显式写出「已连续 N 轮等待」。
7. `AskUserQuestion` 只在人类明显在线且该轮需要即时互动时使用，不要默认用它打断。

## 附一：台面形态（交接台 A / 投递登记台 B）

> 本节是「模板能**确定性生成**出与 `interfaces.md` §一 与 `rounds/prompts/PENDING.md` 等价文件」的依据——字段名与分节写法**逐字对齐**上述两份实填产物。

### (A) 交接台形态（模式 A，P2 原文语义）

- **分节键**：`## [路·<执行者名>]`
- **字段**：枝 / 并行组 / 提示词存盘路径 / **状态（待投 / 投递中 / 已投递）** / 投递时间 / 执行者标识 / 超时阈值
- **各路独立**：独立查重（防双投）、独立锁（「投递中」占位）、独立超时解锁判定（超时 → 回「待投」并上报）
- **写者**：管理者放入待投件（写「待投」）；巡检者取件（写「投递中」）、投递后写「已投递」（**巡检者只改状态字段，不改树**）
- **读后回写**：巡检者每轮结束回写该路状态；管理者在轮次间做修正

### (B) 投递登记台形态（模式 B，子 agent 同步通道现状；本任务 `PENDING.md` 实填形态）

- **文件头注记**（逐字对齐现行 PENDING.md）：`> 用途（依子 agent 同步通道调整）：子 agent 为同步通道，免「取件投递」环节，本台由原「交接台」改为投递登记与审计台——每路登记提示词存盘路径、投递时间、返回状态。管理者写入；执行者与巡检者只读。`
- **分节键**：`## [路·<执行者名>]`（另可含 `## [路·秘书执行者]` 等非作业路）
- **字段**：枝 / 并行组 / 提示词存盘 / 状态 / 投递时间｜返回（返回摘要含产出字节数与后续去向）
- **状态取值**：**待投 / 投递中 / 已投递（RXX，<日期>）——核验通过，已合并 ｜ 未通过，留写区走纠偏**
- **免环节**：无「取件」、无「独立锁」「超时解锁」（同步调用无中间态；调用报错/超时即中断，见 2.2）
- **写者**：**仅管理者写入；执行者与巡检者只读**

## 定时任务提示词的结构（管理者生成，交给人类配置）

```
你是「<任务名>」任务树的管理者大模型。按 task-tree-orchestrator skill 的
scheduler-protocol 执行本轮巡检。项目根：<绝对路径>。树位置：<路径>/task-tree/。
执行者档案：<路径>/task-tree/executors/<执行者名>.md（先读它；多路则逐路读）。

第 0 步：先按 0.1 选定模式——人工投递/多窗口执行者用模式 A，子 agent 同步通道用模式 B
（混合工程逐路选择）；再执行 0.2 铁律检查（按执行者逐个适用，不全局冻结）。
本轮触达后依次执行：
  第 1 步  读树（TREE / rounds / PENDING.md 各路状态 / B0 依赖矩阵与并行组标定 / 各枝）
  第 2 步  逐路判定（对每个有 RUNNING 枝的执行者循环规则①②③；判据按模式分叉——
           A：底层事件配对 + UI 辅证 + size/行数采样；B：Agent 同步返回即判知完成）
  第 3 步  核验交付 + 生成下一轮提示词（管理者专属；先完成先核验，同一时段只核验一路）
          → 通过：下合并指令交秘书执行者；不通过：留写区走纠偏
          → 提示词存盘命名统一 round-R<序号>-<执行者名>-prompt.md
  第 4 步  投递：A 按交接台分路取件（各路独立查重/锁/超时解锁）
                    B 免取件，单条消息内并列 Agent 调用（先登记后投递）
          铁律：同一执行者上一轮未结束不得续投；不同执行者可并行、互不等待
  第 5 步  验证 + 回写（rounds / 各枝状态 / PENDING.md 该路状态 / 执行者档案 / 记忆）
  第 6 步  呈递决策清单（含 P4 并行组汇聚：组内全 DONE 后组级结论一次呈递）
全程中文回复。
```

**注记**：若本任务执行者为**子 agent 同步通道**，第 2 步的「巡检者」环节**豁免**（管理者在 Agent 返回时即判知完成），第 4 步**免取件投递**、交接台降级为投递登记台——即上文的**模式 B**。
